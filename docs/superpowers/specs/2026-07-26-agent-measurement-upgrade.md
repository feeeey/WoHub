## 0. 出发点：四个答不上的问题

Chat agent 的工程可靠性（事件溯源、断线续播、崩溃恢复、构造性红线）在
2026-07 初已经扎实，但以下四个问题当时没有答案：

| 问题 | 升级前的状态 |
|---|---|
| 怎么知道 agent 好不好？改了 prompt 怎么知道没退化？ | 零评测。`CHAT_PROMPT_VERSION` 落进每条 trace 但无任何消费者 |
| agent 会随时间变好吗？ | 不会。outcomes 表 400+ 条真实后验收益躺着没用，语义档案纯静态人写 |
| 记忆架构是什么？ | `HISTORY_LIMIT=20` 硬截断；工具轨迹不回灌（第二轮就重取数）；跨会话零记忆 |
| token 花了多少、哪个工具在退化？ | 逐消息落库但零聚合零展示 |

## 1. 交付内容

### 1.1 三层行为评测（`backend/evals/`，提交 0010c1d、958e7e1）

- **L1 工具选择**：金标用例的 must_call / one_of / must_not_call 约束断言
- **L2 轨迹效率**：调用数、无意义重复（失败后原样重试不罚）、预算纪律
- **L3 答案质量**：system prompt 里的承诺变成可测规则——永不声称已下单、
  结论带数值证据、中文作答、工具全部失败时必须承认证据不足
- 金标 14 条（`evals/golden/core.json`），工具名用 trace 内部名
- **离线模式**（默认，零 LLM 费用）：存量真实轨迹按 prompt_version × model 分桶
- **`--live`**：金标实跑，工具数据由 `evals/fixtures.py` 钉死——两次评测之间
  唯一变量是模型 + prompt
- Settings「Agent 行为评测」卡片：一键运行、轮询进度、历史表带 Δ 对比，
  结果落 `eval_runs` 表
- **关键决策**：live 评测在子进程执行（`evals/service.py`）。fixtures 对
  `agent.tools` 的 patch 是进程级的，进程内跑会让并发 chat 轮次静默拿到假行情

### 1.2 Outcome 闭环（提交 19f50d4）

- `agent/outcome_stats.py`：signals×outcomes 按筛选器 label 聚合方向盲后验
  （1h/4h/24h 上涨占比与均值），10 分钟 TTL 缓存，兼容旧 `label(res)` 编码
- 语义档案每条注入 `↳ 近90天后验（n=…）` 行；样本 <5 显式「样本不足」
  而不是给出无意义占比；方向盲声明写在段落头
- 新工具 `get_screener_stats`：回答「哪个筛选器最近靠谱」
- `OutcomeValidator` 填上 NullValidator 的缝：连续折方向一致性（防单一行情段
  撑起整窗结论）+ 精确二项检验 + 按 spec 内规则数 Bonferroni 校正 + 样本不足
  显式 not_validated。**pass 语义 = 方向声明与后验分布显著一致 ≠ 按此交易可盈利**

### 1.3 chat-v2 迭代（提交 c73e040，评测闭环的完整示范）

基线（chat-v1，0.9875）暴露对比类问题过度采集：relative-strength 用例
8 次调用含 1 次原样重复、5 次 get_indicators 只为比较两个标的。prompt 写入
轨迹效率纪律（先定最小证据集、多标的用一次 snapshot、同参数不重复、够了就答），
版本升 chat-v2，同集重跑：

| 指标 | chat-v1 | chat-v2 |
|---|---|---|
| 总分 | 0.9875 | 0.9917 |
| L2 效率 | 0.9375 | 0.9583 |
| 全集工具调用 | 43 | **26（−40%）** |
| L1 / L3 | 1.0 / 1.0 | 不变 |

诚实残余：relative-strength 0.85 → 0.9，仍超单用例预算 1 次调用。

### 1.4 记忆层（提交 1a031e1）

- **会话摘要**：超出 20 条窗口的历史由主模型增量压缩进
  `chat_sessions.summary`（`summary_upto` 游标；每轮至多一次小压缩调用且仅在
  会话持续增长时发生；失败降级沿用旧摘要、游标不前进下轮重试，绝不阻塞轮次；
  压缩过程以 `history_compress` trace 步骤呈现）
- **证据回灌**：最近 2 条助手消息附工具证据摘要（3 步 × 110 字上限），
  「刚才那个结构再看看」不再重新取数；更早消息仍只回灌正文
- **跨会话记忆**：`agent_memory` 表 + remember/forget 工具，全量注入 system
  prompt。刻意 SQLite 平表 + 50 条 × 200 字硬上限 + 完全相同内容幂等——
  这个规模上向量检索是纯开销，上限逼着做筛选而不是囤积
- 金标 +2：明确偏好必须 save_memory；临时行情观点必须不触发

### 1.5 语义审计入口（提交 c68c7f2）

Settings 语义卡片「后验审计」按钮：每条档案的方向声明对照真实后验出徽章
（数据支持 / 数据不支持 / 样本不足 / 不可检验）。全部可检验声明装进**一个**
validator spec——逐个单独验证会绕过 Bonferroni，把审计自身变成多重检验的
假阳性来源。

### 1.6 用量观测（提交 d922a86）

`GET /agent/usage`：token 按日/按模型聚合 + 从 trace 聚合工具调用数与失败率
（>20% 标红）。零新采集面，纯粹让已落库数据可见。

### 1.7 有护栏的主动性（提交 94f33ce）

任务动作新增 `agent_digest`：信号触发后在「信号简评（自动）」会话创建
**普通 chat 轮次**——不是平行管线，预算/只读工具/红线/trace/评测全部自动
继承，Chat 页可见每次简评的完整工具轨迹。完成后 assistant 文本经
`chat_turns.push_channel_id` 推送任务渠道；推送失败记 push_logs 但不改轮次终态。

护栏（逐条有测试）：agent 未启用跳过（任务本体推送不受影响）、同任务
`cooldown_minutes` 冷却（休眠字段首次有消费者）、简评会话有排队轮次不堆积、
触发文本截断、prompt 要求引用后验统计 / 200 字内 / 证据不足明说。

这是 07-02 被删除的批量裁决层在**有了评测护栏之后**的谨慎重建：
删除 → 建立测量 → 带护栏重建。

### 1.8 事故修复（提交 5e0906d，升级期间由 agent 使用暴露）

第二次 ChartShot 卡死：SSE:000001 的 5m 截图挂 3.6 小时堵死队列（launch/
导航/动作超时已全部在位仍然挂——同步 Playwright 存在不受这些超时管辖的
调用，如 `download.save_as` 等待下载流）。结论：线程内超时打地鼠不收敛，
每个截图 job 改为独立进程组执行，超预算 SIGKILL 整棵树。附带修复带交易所
前缀标的的文件名清洗（`SSE:000001` 含 `:` 被后端白名单拒绝——图落盘成功
但永远取不出来）。

## 2. 系统自己产出的真实发现

升级的价值不在功能清单，在这些**第一次运行就抓到的东西**：

1. 验证器否决自家语义档案：底背离声称偏多，52 条后验 4h 上涨占比 42.3%、
   三折命中率 [0.29, 0.59, 0.39] 方向不一致 → fail；该数字现在直接进 prompt
2. 评测定位轨迹浪费并量化修复：全集调用 −40%，质量三层不掉
3. 观测面首日产出：market_snapshot 失败率 25%（n=4，待观察）
4. 离线评测在 12 条生产轨迹中找到 2 条坏段（重启中断的空消息，L3 0.33）
5. 超卖信号 1h 后验上涨占比 37.4%（n=364）——「超卖=反弹」的直觉被自家
   数据修正，agent 会引用这个数字

## 3. 刻意不做的（同样是决策）

- 多智能体框架：单 agent + 工具在当前任务复杂度是正确选择
- 向量库 RAG：语义档案 + 记忆合计 ~4k token，全量注入即可
- planner/reflection 升级：留待评测证明需要（L2 显示多步任务效率差时再做）

## 4. 已知残余

- relative-strength 仍超单用例预算 1 次（0.9），下一轮 prompt 迭代目标
- L3 是规则断言；LLM-as-judge 未实现（预留 `--judge` 形态）
- 记忆召回（跨会话读取）没有确定性金标用例——live 评测 prompt 含真实 DB
  记忆，无法钉死；只覆盖了写入判断
- 会话持续超窗增长期间每轮多一次小压缩调用（成本换上下文，已知取舍）
- market_snapshot 25% 失败率样本太小，需继续观察
